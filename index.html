A Benchmark for Coding Agents on Evolving Web Applications

We introduce EvoWeb: 320 cumulative requests over 32 web apps. A coding agent builds an app and then keeps extending it, request after request, while a browser agent tests every intermediate version.

The bottom line

Real app development does not stop at the first prompt. People come back to add a feature, change how something behaves, or build on something they asked for last week. Each request lands on code the agent wrote earlier, and it may need that code to keep working.

We evaluated 14 coding models on EvoWeb, each running as an OpenHands agent. No model keeps an app working across the whole trajectory. Fable 5 and Kimi K3 lead with Grades of 0.694 and 0.684, a gap within run-to-run noise. The best models survive about 7.3 of 10 requests, and the weakest reaches a Grade of only 0.162.

Three findings stand out:

  • Making features work together is the hard part. For every model, tests that combine a new feature with an earlier one score lowest, below tests of the new feature alone and re-tests of old ones.
  • Difficulty compounds along dependencies. Late requests that build on longer chains, or on more earlier features, are solved less often.
  • Apps keep building but stop running. Build failures stay rare, but runtime errors climb with every request, from 2% after the first request to about 12% by the last.

Why evolving apps

Tools like Bolt.new and Lovable let people with little or no programming background describe an app and get a working one. The user describes what they want, and the agent decides how to build it. But the first request is rarely the last. A request may depend on state, interfaces or behavior the same agent built several requests earlier. A new feature may work on its own and fail once it has to use that older code, or it may quietly break something that used to work.

Existing web-generation benchmarks score an app built from a single request, or refine an app toward a specification that is fixed in advance. Multi-request benchmarks exist for repository-level software engineering, but not for user-facing apps that grow one request at a time. That leaves one question open:

How reliably can coding agents extend a persistent application over successive user requests while integrating with previously implemented functionality and preserving existing behavior?

One app, ten requests

Here is one real trajectory from the benchmark: app 1, a stock-report generator, built by Opus 4.8. The first request is the original WebGen-Bench prompt. Nine follow-ups grow it into a small investing workspace with a screener, a watchlist, positions, ratings, alerts, transcript search, a comparison tool, a dark theme and a dashboard. Each feature is adapted from a real product, Koyfin or Simply Wall St. The follow-ups also form a dependency graph: positions need the watchlist, and the watchlist needs the screener.

Step through what happened. After every request, the judge (a browser agent) opens the running app and runs five checks: three on the new feature, one that crosses a dependency edge, and one copied from an earlier request. The screenshots are what the judge actually saw, with the numbered element labels it acts on. Click a check to see its expected result, and click a failed one to see its screenshot.

Requests 1 and 2 go well. Request 3 is where it breaks. The screener table grows too wide, and the add-to-watchlist controls end up clipped at its right edge. The watchlist page works and so do most of its checks, but the check that crosses the screener-to-watchlist edge fails. At request 4 the same bug fails again: the integration check needs to add Baltic Freight from the screener, and the backward check, copied from request 3, still finds no "already saved" message. A separate NaN-handling bug costs one more check. One problem at the boundary between two features turns into three failures across two requests.

Then the app recovers: request 5 scores 100%, and so do four of the last five requests. Whether that recovery counts depends on what you assume about the user.

Scoring: how patient is your user?

A sequential benchmark has to decide what happens after a bad request. Most stop at the first failure. That assumes the user leaves immediately, so the app above would be scored on request 1 alone. Scoring every request independently assumes the opposite: a user who keeps going no matter how bad things get. Neither extreme is how people behave, and the patience of the people who will use an agent is unknown.

We do not choose a stopping rule. Each request r gets an accuracy ar, its mean test score with PARTIAL counted as ½. A user with tolerance t keeps going while every request so far scored at least t. Delivered functionality Q(t) averages the accuracy of the requests that user reaches, and unreached requests count as zero. Request survival S(t) counts consecutive requests, from the first, that clear t. Agents run all ten requests regardless of score, so every threshold can be replayed afterwards and the result averaged over all of them:

Grade = ∫01 Q(t) dt = (1/R) Σr ar · mr−1,    Survival = ∫01 S(t) dt = Σr mr,    mr = minj≤r aj

The closed form shows what the metric rewards. An early failure lowers the bar for every request after it, so it costs more than a late one. Trajectories (0.5, 1, …, 1) and (1, …, 1, 0.5) have the same mean accuracy, 0.95, but Grades of 0.50 and 0.95. This follows directly from the user model: a user who gives up early never sees what comes after.

How EvoWeb is built

We designed the benchmark around three properties.

Realistic. We start from 40 randomly sampled app specifications in WebGen-Bench. For each one, a retrieval agent (Sonnet 4.6 with web search) finds two real websites with a similar purpose and extracts three or four notable features from each. A generator (Fable 5) adapts those features into follow-up requests, written in a product owner's voice. The requests describe behavior and pin any data the tests need, but they never prescribe files, components or class names. Grounding matters: in blind pairwise tests, three judges from three vendors preferred the grounded requests 69–74% of the time, and grounding cuts the 4-gram overlap between unrelated apps by 29%.

Cumulative. Before writing any request, the generator lays out a dependency DAG over the ten features. An edge i → j means request j cannot be implemented correctly without request i. Reading the same records doesn't count. Every app needs a dependency chain at least three deep and at least three dependencies between follow-ups. The mean longest chain is 4.75 requests. A separate LLM verifier checks each sequence against twelve rules, a failing sequence gets one repair pass, and people curate the survivors. Of 40 candidates, 32 remain, spanning 16 of WebGen-Bench's 20 domains.

Agentic. Each request runs as a multi-turn OpenHands session with at most 20 agent turns. The repository and the conversation history persist across all ten requests. The agent gets no test feedback between requests, so each request also measures how well it maintains what it has already built.

Five checks per request

Every follow-up carries exactly five browser tests. Three are functional tests of the new feature, and at least one targets the part a shallow implementation gets wrong. One is an integration test along a DAG edge: it acts on the earlier feature and checks the effect in the new one. One is a backward test copied from an earlier request. All 288 follow-up tests are satisfiable: every test gets a full pass in at least two runs of the five strongest models. For 284 of the 288 follow-ups, a single app passes all five of the request's tests at once.

The judge follows WebGen-Bench's protocol: a WebVoyager agent clicks and types through the live app in a fresh browser and returns YES, PARTIAL or NO. We use Sonnet 4.6, a strong computer-use model, to drive it. To validate it, research engineers labeled 300 randomly sampled executions blind to the benchmark verdict, 100 of each test type. The judge agrees exactly with the human label on 87.7% of them (Cohen's κ = 0.72). That rises to 95.0% on the 261 that could be judged from screenshots, while disagreements concentrate in the 39 ambiguous cases that needed live inspection. The mean signed difference from human scores is +0.023 (95% CI −0.004 to +0.051).

What we found

Integration is the hard part

We recompute Grade separately for each test type, keeping each request's gate on its full accuracy so all three are scored over the same trajectories. The order is the same for every model: backward tests score highest, then functional, then integration. Agents generally keep what they built and can build something new. What they find hardest is making the new feature work with the old one.

ModelBackwardFunctionalIntegration

Deeper dependencies, lower accuracy

If composition is the bottleneck, requests that rely on more earlier work should be harder. To separate dependency from position in the trajectory, we look only at the last three requests (8–10), which also cover the widest range of both measures. Accuracy falls with a request's depth in the DAG and with its in-degree, for every model. The fitted lines slope downward everywhere, and they slope most steeply for weaker models.

Apps keep building but stop running

After every request we also record whether the production build fails and whether the served app throws during browser testing. Build errors are rare for most models. Runtime errors vary much more and track Grade more closely (Spearman ρ = −0.72, against −0.52 for build errors). Qwen3.5 35B-A3B, for example, fails to build after 2.5% of requests but throws at runtime after 36.6%. Runtime errors also grow with every request. Models preserve a buildable codebase more often than a working one.

Failed tool calls, such as a string replacement that matches nothing, do not correlate with Grade (ρ = −0.06). The agent sees the failure and retries, so these errors cost steps rather than quality.

Where the failures come from

We classified every failed test (score 0) of four Anthropic models into app-side failure modes. Haiku 4.5's failures are led by missing data or UI (31.2%, against 21–24% for the others). Often each page keeps its own copy of the data, so records added in one request never reach pages added later. Fable 5 rarely breaks the app: 2.2% of its failures are runtime or build errors, against 13.7–17.3% for the others. Its failures shift toward wrong values and styling. It makes the app work and still misses small details.

More effort is not better

Fable 5 scores highest while using the fewest turns per request (4.7). Two of the three strongest models, Fable 5 and GPT 5.6 Sol, each produce about 100K output tokens per trajectory. Sonnet 4.6 produces more than twice as many as Fable 5 and scores lower (Figure 4c). For every model, half the output tokens come in the first three turns. Higher scores come from spending tokens and turns well, although Fable 5 is also the most expensive per app.

The request language matters

Users often describe what they want in their own language, even when the app is in English. We translated the requests into French, German, Chinese, Hindi and Hebrew and left the app and the tests in English. Only Sonnet 4.6 is insensitive, staying within 0.03 of its English Grade in every language. Other models swing in both directions, sometimes in high-resource languages: GLM 5.2 drops to 0.445 in German but reaches 0.602 in Hebrew, and GPT 5.6 Luna falls from 0.277 in English to 0.198 in French. Agents should be evaluated in the language their users write in.

The ranking is not the judge's

LLM judges are known to favor their own outputs, and our default judge, Sonnet 4.6, is also one of the agents we evaluate. So we re-scored every run with three judges from other vendors: GPT 5.6 Terra, GLM 5.3 Flash and Qwen3.5 397B. Absolute scores shift with the judge, but each alternative flips only 2–3 of the 28 model pairs. All the flips are among GPT 5.6 Sol, Opus 4.8 and Sonnet 4.6, which are within 0.015 Grade of each other. No judge favors its own family. Sonnet 4.6 ranks lower under its own judge than under two of the others.

Try it

The harness runs any model: Anthropic, OpenAI, OpenRouter, any OpenAI-compatible API, or weights served locally with vLLM. Build the harness image and install the scorer:

INSTALL
git clone https://github.com/two-delta/EvoWeb.git && cd EvoWeb
docker build -f harness/Dockerfile -t evoweb-harness:latest .
pip install -r requirements.txt && pip install -e .

Then run a model on all 32 apps. The judge defaults to Sonnet 4.6, and the dataset is downloaded from Hugging Face on first use:

RUN
export ANTHROPIC_API_KEY=<key>      # for the judge
evoweb run --name haiku --model anthropic/claude-haiku-4-5

python3 -m evoweb.score_run runs/haiku    # Grade and Survival, scored exactly like the paper

The repository also releases the paper's runs of the four Anthropic models, three runs each with every judge verdict, and one complete Fable 5 run with all conversations, code and judge sessions. The example app above is in examples_artifacts/examples.zip.

Limitations

  • Thirty-two apps of ten requests each is enough to separate model tiers, not to rank models within about 0.01 Grade. The closed models were run three times, the open-weight models once, and the language and DAG analyses have no confidence intervals.
  • The judge is an LLM. Its agreement with people is 87.7% overall but much lower on ambiguous cases, and an error on an early request weighs more under Grade than one on a late request.
  • Uniform weighting over thresholds and PARTIAL = ½ are conventions. Any other weighting falls between the fail-stop score and mean accuracy, and the paper reports both.
  • One backward test per request samples earlier functionality rather than auditing every regression. A failed backward test can also mean the feature never worked.
  • The user never reports a failure or asks for a fix. A closed loop where agents must recover from their own mistakes is the natural next step.

The takeaway

Coding agents are good at building an app from a single request. EvoWeb asks whether they can keep extending that app, and the answer is not yet: even the strongest models leave about 30% of the delivered functionality on the table. The weak point is not new features in isolation. It is the joins between features built at different times, and it gets worse the more an app has already grown. Scoring over every level of user patience shows these gaps without assuming one stopping rule.
